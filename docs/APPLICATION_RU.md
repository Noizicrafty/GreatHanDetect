# Консоль GreatHanDetect

Приложение связывает видео, нейросетевой инференс, трекинг, временное правило, доказательство, журнал и интерфейс оператора. Клиент LinQ использует реальный AMQP-протокол стенда; локальный CPU-путь использует ONNX Runtime. Режим `replay` служит только проверке приложения и заметно помечается в кадре, интерфейсе и событиях.

## Установка и запуск

Клиент проверяется на Python 3.12; серверный пример организаторов работает на Python 3.11. Для компиляции SDK требуется отдельная Linux x86_64 среда **Python 3.12.11** и TPU Framework **2026.9.45**. Не устанавливайте SDK компилятора в рабочее клиентское окружение.

Windows:

```powershell
.\setup_application_windows.bat
.\START_APPLICATION_WINDOWS.bat
```

Linux:

```bash
bash setup_application.sh
bash start_application.sh
```

Консоль открывается по адресу `http://127.0.0.1:8080`. Другой порт: `python -m greathan --port 8081`. Другая конфигурация и отдельная история: `python -m greathan --config configs/application.yaml --data results/my_run`.

При отсутствии файла модели приложение показывает ошибку, а журнал остаётся доступен. Модели поставляются отдельным комплектом; распакуйте его в корень репозитория с сохранением `assets/`. Не копируйте SDK, VPN-профиль или пароли в открытый репозиторий.

## Подключение LinQ

1. Подключите выданный организаторами VPN. Для сохранения обычного подключения к интернету используйте согласованный маршрут к сети стенда.
2. Из личного Jupyter скачайте `packages/tpu_pycloud_format-0.0.1-py3-none-any.whl` и установите в клиентскую `.venv`:

```powershell
.venv\Scripts\python.exe -m pip install "C:\Downloads\tpu_pycloud_format-0.0.1-py3-none-any.whl"
```

3. Задайте **учётные данные брокера из example.ipynb**, не VPN-пароль:

```powershell
$env:LINQ_AMQP_USER = '<broker user>'
$env:LINQ_AMQP_PASSWORD = '<broker password>'
```

4. В конфигурации задайте `backend: linq_amqp`, адрес брокера `10.0.114.30:5672`, exchange `tpu.direct`, routing key `input` и абсолютный путь программы в `/auto/cache/<команда>/`.
5. Программа должна находиться на сервере и быть доступна воркеру. Локальный путь Windows не подходит для `remote_program`.
6. Выполните проверку одного изображения перед видео:

```bash
python tools/check_model.py --config configs/application.yaml --image /path/to/image.jpg --warmup 2 --requests 20 --out results/model_check
```

Клиент проверяет ID ответа, код состояния воркера, имена, формы, типы и конечность значений тензоров. Он хранит одно активное соединение и временную эксклюзивную очередь, выполняет запросы последовательно и закрывает транспорт после ошибки. Следующий вызов подключается заново. Автоматического перехода с TPU на CPU нет.

## Работа оператора

В «Настройках источника» укажите камеру, видео, сценарий и backend. Настройки меняются после остановки обработки. Для файла есть предпросмотр. Полигон зоны можно нарисовать по вершинам либо задать JSON с координатами от 0 до 1.

После запуска консоль показывает обработанный кадр, активный backend, позицию видео, фактический FPS, p95 инференса, число событий и пропусков. При ошибке источника или TPU появляется явное состояние ошибки/сбоя. Последний кадр не является свидетельством продолжающейся безопасной работы.

Подтверждённое событие сразу попадает в SQLite и очередь оповещений. Карточка содержит камеру, зону, время, позицию видео, кадр, причину и версию модели. Оператор может принять событие в работу, подтвердить или пометить ложным, добавив комментарий. Журнал фильтруется по типу, камере, зоне и времени; фильтры сочетаются. Есть экспорт CSV.

При открытии страницы история не выдаётся за новые тревоги. Переподключение продолжает чтение очереди с последнего курсора. Одно событие имеет одну запись оповещения. При перезапуске незавершённые исторические события получают состояние `interrupted`.

## Источник времени и нагрузка

- `offline`: все выбранные для анализа кадры обрабатываются на максимальной скорости. Это не имитация реального времени.
- `realtime`: воспроизводится временная шкала файла; если backend отстаёт, старые кадры пропускаются. Позиция берётся из PTS, при недоступности — из FPS файла.
- `live`: сетевой поток через FFmpeg, отдельный читатель и очередь размером один кадр. Поддержаны тайм-ауты открытия/чтения. Реальный RTSP-поток в текущем приёмочном наборе отсутствует; локальная USB-камера этим режимом не поддерживается.

Для файлов календарное время событий привязано к моменту запуска и позиции видео, а не к дате реальной съёмки. Позиция внутри видео хранится отдельно. Интерфейс показывает московское время.

При недостаточной скорости уменьшайте `analysis_fps` и проверяйте влияние на временное правило. Пропуск кадров не равнозначен отсутствию нарушения. Простая IoU-ассоциация удерживает ID при коротких перекрытиях; она не гарантирует личность при долгом исчезновении, резком перемещении или плотной толпе.

## Сценарии и расширение

Правило опасной зоны использует точку основания рамки человека, нормированный полигон и временное подтверждение. Правило курения использует детекции объектов, позу и временные признаки; объектное подтверждение включено по умолчанию. Семантика классов задаётся явно: в Roboflow `smoking-tasfx/4` класс `smoking` на проверенных обучающих примерах размечает сигареты, поэтому он объединяется с `Cigarette`, а не превращается в метку поведения человека.

Новая модель добавляется через именованный контракт входов/выходов и CPU-декодер, новое правило — через `evaluate`, возвращающий `RuleResult`. Хранение событий, доказательства и уведомления общие. Наличие пункта в каталоге расширений не означает наличие проверенной модели.

## Где находятся результаты

В `--data` хранятся:

- `journal.sqlite3` — события, решения оператора, очередь уведомлений, диагностика и прогоны;
- `evidence/<event_id>.jpg` — подтверждающие кадры;
- `runs/<run_id>/frames.csv` — сырые покадровые измерения;
- `runs/<run_id>/inference.jsonl` — транспортные тайминги и ID реальных запросов;
- `runs/<run_id>/summary.json` — сводка;
- `runs/<run_id>/annotated.mp4` — обработанное видео, если включено.

Файл `runtime_config.json` содержит сохранённые настройки этого экземпляра. При следующем запуске с тем же `--data` он имеет приоритет над `--config`.

`/api/delivery-metrics` измеряет время от создания события до подтверждения браузером его показа. Отдельная метрика для `realtime` включает путь от временной отметки подтверждающего кадра через инференс, журнал и интерфейс. Серверное поле `worker.inference_time` сохраняется с суффиксом `_raw`: его единицы/границы не подменяют клиентскую задержку.

## Проверка и границы утверждений

```bash
python -m compileall -q greathan tools tests
python tools/bootstrap_source.py
python -m unittest discover -s tests -v
python tools/make_app_demo.py
python -m greathan --config assets/demo/replay_config.json --data results/qa
```

Последняя команда использует тестовые детекции. Она проверяет события и интерфейс, а не нейросеть. Для проверки LinQ нужны фактические запросы к собственной прикладной программе и соответствующие сырые результаты.

Фотографии, превращённые в ролик, позволяют проверить нейросетевой и программный путь, но не заменяют CCTV и разметку эпизодов. Метрики детектора на изображениях и метрики событий публикуются отдельно. Полевая точность, частота ложных тревог за смену и работа нескольких реальных камер требуют отдельной проверки.
