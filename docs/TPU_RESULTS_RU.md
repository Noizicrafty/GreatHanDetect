# GreatHanDetect: исполнение на LinQ TPU и ускорение

Проверено 25.10.2026 (Москва). Существующий checkpoint после 26 эпох экспортирован и исполнен через организаторский сервис LinQ. Новое обучение и SDK fine_tune не запускались.

## Что развёрнуто

Публичный сайт: https://linq.user-link.xyz/03_cameras.html → «Веб-камера» → «LinQ TPU · O1» → «Запустить». После обновления Ctrl+F5 доступны пределы 2, 5 и 10 FPS. Это предел запросов, фактическая скорость измеряется отдельно в интерфейсе.

Путь: камера браузера → контур губ в Web Worker → JPEG области лица → HTTPS/Nginx → ограниченный SSH reverse tunnel → HTTP-сервис командного Jupyter → FP32 letterbox 416×416 → AMQP → LinQ TPU → CPU NMS → JSON → упорядоченная разметка кадра. Внешний канал передаёт JPEG/JSON, а не FP32-тензоры. CPU можно выбрать явно; TPU-режим не подменяется CPU при ошибке. Сохранение срабатывания в журнал включает отдельную CPU-проверку и обозначено в интерфейсе.

На Jupyter запущен `serve_webcam_tpu.py`, привязанный только к `127.0.0.1:8094`. На публичном хосте relay слушает только `127.0.0.1:18094`. Ключ разрешает этот forward, без shell/SFTP и произвольных портов. Он не входит в пакет доказательств. HTTPS остаётся на существующем домене и сертификате. Доступ root потребовался для Nginx, обновления UI и ограниченного relay; компиляция и измерения TPU выполнены в Jupyter.

В последнем браузерном прогоне предел был 5 FPS. В наблюдённом последнем кадре отображались 64 мс inference и 297 мс полного цикла; это одно наблюдение, не p95. После «Остановить» видеотрек перешёл в ended. Кадры автоматически не сохранялись и события в журнал не добавлялись.

Браузерные проверки использовали виртуальное видеоустройство Chromium с повторяемым диагностическим изображением №4. Это проверка захвата/транспорта/исполнения/отрисовки, не тест живого человека и не измерение качества видеособытий. FPS считается по временам завершения ответов; интерфейс отдельно считает применённые по порядку результаты. Скорость зависит от общей нагрузки LinQ и сети. O1 и O5 запускались последовательно на общем сервисе, без изоляции нагрузки; из этих прогонов нельзя заключать, что O5 всегда медленнее.

## Качество пока не принято

На девяти ранее выбранных test-изображениях выполнено сопоставление cigarette один-к-одному с имеющейся разметкой при IoU ≥ 0,5 и confidence ≥ 0,25. CPU ONNX 416: сопоставлены 9 GT, одна несопоставленная детекция. TPU: сопоставлены 8 GT, одна пропущена, семь детекций не сопоставились. Среди лишних боксов есть дубли; существующая разметка также может быть неполной. Эти числа не являются итоговыми precision/recall и не оценивают события курения.

Confidence после PTQ снижается; O1 и O5 на этих девяти входах дали одинаковые хеши выходных тензоров. Успех компиляции, высокая скорость и девять положительных примеров не доказывают 98% accuracy. Для приёмки нужны более широкая независимая оценка и реальные ролики.

## Что ускоряет систему и что пробовать дальше

1. **Размещать предобработку и NMS рядом с LinQ — реализовано.** Один FP32-вход занимает 2 076 709 байт в сообщении, выход четырёх классов — около 113 648 байт. Диагностический JPEG с JSON/base64 занимал 75 113 байт. Передача JPEG через внешний канал снимает значительную сетевую нагрузку. Для 3 FPS один вход FP32 требует примерно 49,8 Мбит/с без накладных расходов; JPEG такого размера — около 1,8 Мбит/с. Эти размеры относятся к конкретному кадру, не универсальны.
2. **Перекрывать внешний канал двумя запросами — реализовано.** В браузере допускаются максимум два незавершённых/ожидающих применения кадра. Результаты применяются по порядку захвата, отрицательный поздний результат не теряется. Каждый кадр хранит собственную геометрию. На сервере два выделенных потока с раздельными pika-соединениями; соединения не пересоздаются на каждый JPEG и поддерживаются heartbeat. В данном сравнении браузерный FPS вырос с 2,61 до 4,44.
3. **Для нескольких камер исследовать 2–4 RPC в полёте.** Замеры дают запас пропускной способности сервиса, но p95 увеличивается. Нужны ограничение возраста кадра, fairness между камерами и запрет бесконечной очереди. Один pika-канал между произвольными потоками не разделять. Число запросов в полёте не равно batch и не доказывает производительность одного TPU.
4. **Сравнивать O1/O3/O5 на одинаковых входах и контролировать нагрузку.** По SDK 2026.9.45 O5 позволяет перекрывать подгрузку весов DTS с вычислением ME, использовать вторую DDR, эффективнее размещать тензоры в cache и выполнять layer fusion. Это реальные механизмы LinQ, а не обещание автоматического ускорения. Здесь O5 не улучшил наблюдаемый RPC; оставлен O1. В документации есть предупреждение о возможных некорректных/долго компилирующихся O5-программах. Источник: `tpu_framework.pdf`, раздел 4.3, печатные стр. 16–17 (PDF стр. 20–21).
5. **Проверить меньший вход только совместно с ROI.** 320×320 содержит примерно 59% пикселей от 416×416, но реальное ускорение не обязано совпасть с этим отношением. Для мелкой сигареты уменьшение всего кадра рискованно. Следующий эксперимент — crop лица/губ с запасом, отдельная программа 320 и честное сравнение пропусков с 416. Генеративное дорисовывание сигареты не использовать.
6. **Улучшать PTQ под распределение ROI, без обучения.** Сравнить калибровку на train-full/train-crop, max и документированные percentile-настройки SDK. Не подбирать пороги по этим девяти test-кадрам. Более широкий calibration-набор при max-порогах может ухудшать результат из-за выбросов; SDK поддерживает samplewise_percentile. Проверять качество до сравнения скорости.
7. **Batch 2/4 — отдельный эксперимент для нескольких камер.** SDK поддерживает batch у Network, но нужны новая программа, соответствующие сигнатуры и batch-aware decoder: текущий decoder принимает batch 1. Ожидание заполнения batch может ухудшить интерактивную задержку, поэтому нельзя просто поменять параметр в текущем сервисе.

Главный следующий шаг по качеству — независимые отрицательные сцены «телефон/ручка/еда/пар», профиль и перекрытия, затем проверка событий на видео. Главный следующий шаг по скорости — длительный многокамерный тест с ограничением возраста кадра и контролем внешней сети.

## Эксплуатационные пределы

TPU-режим зависит от доступности Jupyter и сервиса организаторов. SSH relay переподключается при разрыве. При остановке командного Jupyter процессы потребуется запустить снова. CPU остаётся отдельным явным режимом. Успешная демонстрация не заменяет долговременную приёмку, роли операторов и производственную оценку.
